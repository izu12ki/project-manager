# 外部 REST API 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** アドミンが API キーで `/api/v1` を呼び、課題の参照・起票・更新（1 件・一括）をできるようにする。招待とユーザー一覧でアドミンロールを扱えるようにし、AI エージェント用の Skill を同梱する。

**Architecture:** API は SvelteKit の `+server.ts` に置く。`hooks.server.ts` で `/api/v1/` を Cookie 認証から外し、Bearer キーから `Actor` を組み立てる。書き込みは既存サービス層を通す。一括操作は、検証と書き込み内容の組み立てを `issue-input.ts` に切り出し、1 回の `db.batch` で書き込む。一括操作の通知は新しい通知種別で、受信者ごとに 1 件にまとめる。

**Tech Stack:** SvelteKit / Cloudflare Workers / Drizzle (libSQL, Turso) / valibot / vitest / Playwright

**Spec:** `docs/superpowers/specs/2026-10-25-rest-api-design.md`

## Global Constraints

- ロールは `admin | member | guest` のまま。API を使えるのは admin だけ（`api:use`）。
- API キーの形式は `pm_` + `randomToken()`。DB には `sha256Hex` の値だけを保存する。平文は作成時に一度だけ返す。
- レート制限: キーごとに `{ windowMs: 60_000, max: 120 }`。キーは `app:api:<apiKeyId>`。
- 一括 API の上限は 1 リクエスト 100 件。`?dryRun=true` は検証だけ行い、何も書かない。
- API の応答にメールアドレスを含めない。ユーザーは `{ id, name }` で返す。
- エラーの形は `{ error: { code, message, fields? } }`。HTTP ステータスの対応は `validation 400 / unauthorized 401 / forbidden 403 / not_found 404 / conflict 409 / rate_limited 429`。
- 一括のエラーでは、`fields` のキーを `items.<index>.<field>` にする（index は 0 始まり）。
- 日付は `YYYY-MM-DD`。API の `null` は「空にする」を意味し、サービスへは `''` として渡す。
- 変更履歴・通知・報告者はすべてキーの持ち主として記録する。
- マイグレーションは `pnpm db:generate` で作り、生成された SQL を確認してからコミットする。
- コミットの形式は `feat(web): ...` / `docs: ...`。各タスクの終わりに `pnpm check` と `pnpm test:unit` が通ること。

## Review Focus

1. **アドミンでなくなった人のキー**: 降格・無効化された持ち主のキーは、次のリクエストで 401 になること。Task 3 でテストする。
2. **途中に不正な要素がある一括起票**: 1 件でも不正なら、課題・採番・変更履歴・通知のどれも書かれないこと。Task 7 でテストする。
3. **一括起票と、画面からの起票が同時に起きたとき**: 課題番号が重複しないこと。採番をバッチ内の副問い合わせで行うことで防ぐ。Task 7 でテストする（一括の直前と直後に画面からの起票を挟む）。
4. **一括更新で同じ番号が 2 回出てくる要素**: 400 で拒否すること。Task 7 でテストする。
5. **member が受け取るまとめ通知**: 自分が参加していないプロジェクトのまとめ通知は見えないこと。Task 8 でテストする。

**Interfaces:**
- Produces:
  - `type FieldSets = { statuses: StatusDef[]; typeIds: Map<string, string>; categoryIds: Map<string, string>; milestoneIds: Map<string, string>; assignable: Map<string, string> }`（id → 名前）
  - `loadFieldSets(db: DB, projectId: string): Promise<FieldSets>`: 並列に 5 本の問い合わせを行う。
  - `prepareCreate(actor: Actor, fields: FieldSets, input: unknown): CreateValues`
    - 同期関数。検証と権限チェックを行い、insert する値（number と position 以外）を返す。
    - エラーは既存の `createIssue` と同じ `AppError` を投げる。
  - `preparePatch(actor: Actor, fields: FieldSets, cur: IssueRow, input: unknown): IssuePatch`
    - 同期関数。既存の `updateIssue` の判定をそのまま移す。position は含めない。status の変更有無だけを返す。
  - `describeChanges(fields: FieldSets, cur: IssueRow, patch: IssuePatch): IssueChangeItem[]`
    - 同期関数に変える。名前は `fields` から引く。担当者の旧値が担当可能でない人のときは、`user` から名前を引く必要がある。その分だけ `loadFieldSets` 呼び出し側で補う。
  - `bulkCreateIssues(ctx, key, input: unknown, opts: { dryRun: boolean }): Promise<{ numbers: number[] }>`
    - 入力は `{ items: CreateInput[] }`。1〜100 件。dryRun のときは `numbers: []` を返す。
  - `bulkUpdateIssues(ctx, key, input: unknown, opts: { dryRun: boolean }): Promise<{ numbers: number[] }>`
    - 入力は `{ items: ({ number: number } & UpdateInput)[] }`。1〜100 件。
  - `BULK_MAX = 100`
- 採番のアルゴリズム（この形で書くこと）。バッチは「挿入 → 採番更新」を 1 件ずつ交互に並べる。

```ts
// 各要素について: 現在の nextIssueNumber を番号にして挿入し、その後 +1 する。バッチは 1 トランザクション。
for (const v of values) {
	stmts.push(db.insert(issue).values({ ...v, number: sql`(select ${project.nextIssueNumber} from ${project} where ${project.id} = ${p.id})` }));
	stmts.push(db.update(project).set({ nextIssueNumber: sql`${project.nextIssueNumber} + 1` }).where(eq(project.id, p.id)));
}
```

  - position は、ステータスごとに `generateNKeysBetween(max, null, n)` で一度に作る。
  - 一括更新では、status が変わる要素にだけ position を振る。変更履歴は `describeChanges` が空でない要素ぶんだけ insert し、同じバッチに入れる。
  - 書き込み後に `linkAttachments` を呼ぶのは、本文が変わった要素だけにする。
