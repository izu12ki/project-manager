# 外部 REST API 設計書

日付: 2026-10-25
前提: `2026-10-09-project-manager-design.md`（以下「本体設計書」）の権限・データモデル・エラー処理、`2026-10-14-notifications-design.md` の通知の仕組みに従う。

## 1. 目的とスコープ

PM・ディレクターが Claude Code などの AI エージェントから課題をまとめて起票し、既存のタイムライン（ガントチャート）でプロジェクト全体のスケジュールを組み立ててチームに共有できるようにする。起票にミスがあれば、同じ API で後から直せること（例: 全体を 1 週間後ろにずらす、担当者を付け替える）。

AI エージェントへの API の教え方は「ドキュメントを読ませて curl で呼ばせる」方式とし、そのための Skill をリポジトリに同梱する。本システムは OSS として配布する予定なので、Skill も配布物の一部として扱う。

API を使えるのはアドミンだけ。あわせて、招待でアドミンロールを選べるようにし、ユーザー一覧から後でロールを変更できるようにする。

### 含む

- アドミン用の個人 API キー（発行・一覧・無効化）
- REST API `/api/v1`: 参照（プロジェクト・課題）、課題の起票・更新（1 件・一括）
- 一括操作の通知を受信者ごとに 1 件にまとめる
- 招待でのアドミンロール選択、ユーザー一覧でのロール変更
- Skill（`skills/project-manager/`）と API リファレンス

### 含まない

- 課題の削除、コメント、添付ファイル、プロジェクト設定（ステータス・種別・カテゴリ・マイルストーン）の作成・変更を API から行うこと
- MCP サーバー
- アドミン以外のロールへの API 開放、キーごとの権限（スコープ）の設定
- API キーの有効期限
- OAuth などキー以外の認証方式
- OpenAPI 仕様の自動生成（ドキュメントは手書きの Markdown）

### 避けたいこと（動いても失敗とみなす）

- API 経由の操作が画面からの操作と違う結果になる（権限チェック・変更履歴・通知が抜ける、など）。必ず既存のサービス層を通す。
- 一括操作の途中で失敗し、一部だけ作られた状態が残る。
- ガント 1 本の起票で担当者に数十〜数百件の通知が届く。
- API の応答に含まれたメンバーのメールアドレスが AI の提供元に送られる。応答にメールアドレスを含めない。
- 特定の環境（本番 URL、組織名）に依存した Skill になる。

## 2. 権限とロール

- ロールは今と同じ admin / member / guest の 3 つ。「アドミン以上」はアドミンのみを指す。
- API キーの発行・利用はアドミンだけに許可する。`authz.ts` に `api:use` を追加する（admin のみ true）。
- API リクエストの実行者（`ctx.actor`）は、キーの持ち主のユーザーとする。変更履歴・通知・報告者は、その人の操作として記録する。
- ロールと無効化状態はリクエストのたびに DB から読む。持ち主がアドミンでなくなったり無効化されたりしたら、キーは即座に 401 を返す。キーそのものは消さないので、アドミンに戻ればまた使える。

### 招待でのアドミン選択

- `invitation.role` の enum に `admin` を足す（マイグレーションが発生する）。招待画面のロール選択肢に「アドミン」を追加する。
- アドミンは全プロジェクトにアクセスできるが、招待時の「参加プロジェクト」は今と同じく必須のままにする（担当者候補に出すために必要）。（私の判断）

### ユーザー一覧でのロール変更

- `/admin/users` の各行でロールを変更できるようにする。サービス `changeUserRole(ctx, userId, role)` を追加し、`user:manage` で認可する。
- 自分自身のロールは変更できない。また、有効なアドミンが 0 人になる変更（最後のアドミンの降格）は拒否する。（私の判断）
- 降格しても、プロジェクトのメンバー登録はそのまま残す。アドミン時代に参加していなかったプロジェクトは見えなくなる。（私の判断）
- 降格した人のログイン中セッションは消さない。ロールは毎リクエスト読み直しているので、次の操作から新しいロールが効く。（私の判断。実装時に `hooks.server.ts` がセッションのキャッシュからロールを読んでいないか確認すること）

## 3. API キー

- 保存先は新テーブル `api_key`。列は `id`、`user_id`、`name`、`token_hash`（SHA-256、一意）、`prefix`（表示用の先頭数文字）、`last_used_at`、`revoked_at`、`created_at`。
- 平文は作成直後に一度だけ表示する。形式は `pm_` に続けて `randomToken()` の値を付ける。`pm_` は漏洩スキャナで見つけやすくするための接頭辞。
- 1 人が複数のキーを持てる。名前（例:「Claude Code 用」）は必須。
- 管理画面は `/account` に「API キー」の欄として足し、アドミンにだけ表示する。一覧には名前、接頭辞、作成日、最終利用日時を出し、個別に無効化できる。無効化は取り消せない。
- 有効期限は設けない。
- 最終利用日時は毎リクエスト書き込まず、前回から 1 分以上経っているときだけ `waitUntil` で更新する。（私の判断）
- アドミンが他人のキーを見たり消したりする機能は今回作らない。持ち主を無効化すれば、その人のキーはすべて止まる。

## 4. REST API

### 共通

- ベースパスは `/api/v1`。SvelteKit の `+server.ts` で実装する。`hooks.server.ts` で `/api/v1/` を Cookie 認証とログインへのリダイレクトから外し、`Authorization: Bearer <key>` で認証する。Cookie のセッションでは呼べない（CSRF 対策のため）。
- やり取りは JSON。日付は `YYYY-MM-DD`、日時は ISO 8601。
- 課題は画面と同じ表記（`PROJ-12`）で指定する。パスでは `/projects/{key}/issues/{number}` の形にする。
- 担当者、種別、カテゴリ、マイルストーンは ID で指定し、ステータスはキーで指定する。それぞれの値はプロジェクト詳細 API で一度に取れる。メールアドレスによる指定は受け付けない。
- 応答のユーザーは `{ id, name }` だけを返し、メールアドレスを含めない。
- エラーは `{ error: { code, message, fields? } }` の形で返す。`code` は既存の `AppError` の種類に合わせ、HTTP ステータスは validation 400、unauthorized 401、forbidden 403、not_found 404、conflict 409 とする。`fields` には項目ごとの理由を入れ、AI が読んで自分で直せる文にする。メッセージは日本語。
- レート制限は既存の `consumeRateLimit` を使い、キーごとに 1 分あたり 120 リクエストとする。超えたら 429 を返す。（私の判断）
- アーカイブ済みプロジェクトへの書き込みは、画面と同じ扱いにする（サービス層の挙動に従う）。

### エンドポイント

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/v1/me` | キーの持ち主（id, name, role）。接続確認用 |
| GET | `/api/v1/projects` | 見えるプロジェクトの一覧 |
| GET | `/api/v1/projects/{key}` | プロジェクト詳細。ステータス、種別、カテゴリ、マイルストーン、担当可能メンバー（id, name）を含む |
| GET | `/api/v1/projects/{key}/issues` | 課題一覧。ステータス・担当者・マイルストーン・種別・カテゴリで絞り込める（`listIssues` の絞り込みに合わせる）。ページングあり |
| GET | `/api/v1/projects/{key}/issues/{number}` | 課題詳細（本文を含む） |
| POST | `/api/v1/projects/{key}/issues` | 1 件起票 |
| PATCH | `/api/v1/projects/{key}/issues/{number}` | 1 件更新。送った項目だけ変える。`null` は値を空にする |
| POST | `/api/v1/projects/{key}/issues/bulk` | 一括起票（最大 100 件） |
| PATCH | `/api/v1/projects/{key}/issues/bulk` | 一括更新（最大 100 件。各要素に `number` と変更項目を入れる） |

起票・更新で扱う項目は、タイトル、本文、種別、ステータス、完了理由、優先度、担当者、開始日、期限日、カテゴリ、マイルストーン。

- 本文は画面と同じ形式で受け取る。画面のエディタが Markdown を保存しているなら Markdown を受け取る。実装時に確認すること。
- 起票・更新の応答には、作成・更新後の課題（番号を含む）を返す。

### 一括操作

- 全件成功か全件失敗のどちらかにする。まず全件を検証し、1 件でも不正なら何も書かずに 400 を返す。`fields` は `items.3.dueDate` のように何件目かが分かる形にする。
- 書き込みは 1 回の DB バッチ（`db.batch`）にまとめる。課題番号の採番（`project.nextIssueNumber`）も同じバッチの中でまとめて進める。
- 上限 100 件は、Workers の 1 リクエストあたりのサブリクエスト数と CPU 時間に収めるための値。実装時に 100 件で実測し、収まらなければ下げる（ドキュメントと Skill も合わせて直す）。
- 一括 API は `?dryRun=true` を受け付ける。検証だけ行い、何も書かずに結果を返す。100 件を超える作業では、Skill がまず全チャンクを dryRun で検証してから書き込むことで、検証エラーによる途中失敗を防ぐ。それでもチャンクの途中で失敗した場合（障害など）は、成功済みのチャンクは残る。Skill は成功・失敗したチャンクを報告する。（私の判断）
- まとめ通知はリクエスト（チャンク）ごとに送る。300 件なら担当者 1 人あたり最大 3 件になる。リクエストをまたいでまとめる仕組みは作らない。（私の判断）
- 再送による重複起票を防ぐ仕組みはサーバー側に作らない。Skill に「タイムアウトや通信エラーの後はやみくもに再送せず、課題一覧で作成済みかを確認してから続きを送る」と書く。（私の判断）
- 一括操作の中身は、1 件 API と同じ検証・変更履歴の記録を通す。既存の `createIssue` / `updateIssue` を 1 件ずつ呼ぶとバッチにまとめられないので、検証と書き込み内容の組み立てを関数に切り出し、1 件 API と一括 API の両方から使う形にする。

## 5. 一括操作の通知

- 1 件 API の通知は画面と同じ。
- 一括 API では、1 件ずつの通知を送らない。代わりに、本来通知を受け取るはずだった人ごとに 1 件の「まとめ通知」を送る。
  - 例: 「平野さんが PROJ で 30 件の課題をあなたに割り当てました」「平野さんが PROJ の課題 12 件を更新しました」
  - 受信者の計算は既存の `planNotifications` を各課題に適用した結果を集計して行う。自分自身への通知を除くなどの既存ルールはそのまま効く。
- まとめ通知は、アプリ内通知と Slack DM（連携している人のみ）に 1 件ずつ送る。現状メール通知はないので、メールでは送らない。
- `notification.issue_id` は今は必須なので、まとめ通知用に次の変更を入れる（マイグレーションが発生する）。
  - `issue_id` を null 可にする。
  - `project_id` と `count` を追加する。
  - 種別に `bulk` を追加する。
- まとめ通知のリンク先は、そのプロジェクトの課題一覧（割り当てなら担当者が自分で絞り込んだ状態）にする。
- 細かな文面や、割り当てとステータス変更が混ざったときの見せ方は実装者に任せる。

## 6. Skill とドキュメント

- 置き場所はリポジトリ直下の `skills/project-manager/`。`.claude/skills/` に置くと、このリポジトリの開発者向けに読み込まれてしまうので避ける。
  - `SKILL.md`: いつ使うか、環境変数、作業手順。
  - `reference.md`: エンドポイント、項目、エラーの API リファレンス。
- 接続先 URL と API キーは環境変数 `PM_API_URL` と `PM_API_KEY` で渡す。Skill には特定の URL を書かない。
- 作業手順に含めること:
  1. `GET /me` で接続を確認する。
  2. プロジェクト詳細を取得し、ID とステータスキーを把握する。
  3. 起票前に、課題の一覧（タイトル、担当、開始日、期限日）をユーザーに見せて確認を取る。
  4. 100 件ごとに分け、全チャンクを dryRun で検証してから一括起票する。失敗時は再送前に課題一覧で作成済みかを確認する。
  5. 最後にタイムライン画面の URL を伝える。
  - 修正のときは、課題一覧を取得して対象を特定し、変更内容を見せて確認してから一括更新する。
- README に、API キーの発行方法と Skill の導入方法（`~/.claude/skills/` へのコピー）を追記する。

## 7. テスト

- サービス層の単体テスト:
  - API キーの検証（無効化済み、持ち主の降格・無効化）
  - ロール変更の制約
  - 一括起票・更新（全件ロールバック、採番、変更履歴）
  - まとめ通知の集計
- `/api/v1` の結合テスト: 認証なしは 401、member のキーは 401、正常系、一括の上限超過。
- E2E: 招待でのアドミン選択、ユーザー一覧でのロール変更、API キーの発行と無効化。

## 8. デプロイ時の注意

- マイグレーションは 2 本ある。`api_key` テーブルの追加と、`invitation.role` / `notification` の変更。本番より先にプレビュー DB に適用する（CLAUDE.md の手順に従う）。
- `notification.issue_id` を null 可にするには、SQLite ではテーブルの作り直しが必要。drizzle-kit が作るマイグレーション SQL を確認してから適用する。
